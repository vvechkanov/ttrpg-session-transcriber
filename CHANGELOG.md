# Changelog

## [Unreleased]

### Added
- Timezone anchor measured from the combat dump: `Бой*.txt` timestamps are UTC while the chat export is browser-local, so the offset between them can be measured instead of guessed. Independent of the machine running the merge
- Coverage warning when the Craig recording starts after the session did — names how much chat and which encounters have no audio behind them, on the session screen before the run rather than in the output after it
- `CONTRIBUTING.md` now says when the tier-2 end-to-end run is owed — before a release, and on changes to `sources/`, `mergers/`, `renderers/`, `core/` or `domain/` — everything the run reads. CI has never run that suite and, by decision, will not: it needs a ~3.2 GB model bundle (ADR-022). `tests/test_tier2_e2e_gate.py` guards the mechanical half — that the suite still carries both markers, and that no pytest invocation in `ci.yml` collects it
- ADR-021 records why screen invariants are checked by geometry rather than by pixel screenshots: the same four screens regenerated on Linux differ from the committed Windows captures in every file size, because the capture script registers Windows-only font paths. It also records what `scripts/dump_qml_geometry.py` actually flags today — zero width or height — as against the two further checks its own docstring claims and does not implement

### Changed
- `docs/process.md` no longer instructs the night agent to run `gh`, and §6's audit no longer stops the night when a tool is missing. The cloud runner has no `gh` binary, and installing one does not help: the session's GitHub credentials serve only a pinned set of PR-review operations, so everything else answers 403. §6 step 1 gated the entire run on `gh` being functional, and it was obeyed exactly as written — thirteen consecutive nights of audit, summary, exit, with nothing built, while master stayed green and ten cards sat ready. The gate was not wrong when it was written; it outlived the ability it was protecting. Every step that used `gh` now names a call that works — `create_pull_request` to open the PR, `pull_request_read method=get_check_runs` to read its checks, `merge_pull_request` to merge, `actions_list` to inspect a CI run — and the one step that needs no API at all, fetching a PR head, is plain `git fetch origin pull/<N>/head`. That last one is written down as deliberately non-MCP so nobody "finishes the migration" by reaching for a call that does not exist. In place of the gate the audit now records a missing tool as a fact for the summary and a reason to look for a replacement, and §4 is stated to run regardless, because refining a wish touches GitHub not at all. Two things that survived the swap and should not have: the merge condition still described checks in the vocabulary of the removed CLI — `pending` and `fail`, words that appear nowhere in a check-run, whose fields are `status` and `conclusion` — and an agent hunting for `pending` would have found it on the neighbouring `get_status`, which reports `state: pending` forever on this repository because it has no legacy statuses at all; and the merge recipe checked the PR head out under a name of its own, leaving a branch with no upstream that the loop's own "fix and push" step had no working push for. Both are now written in the terms of the calls that serve them. `tests/test_process_review_signals.py` guards all of it: no `gh` subcommand anywhere in the document, no halting phrase in any section, the lesson that replaced the gate pinned so it cannot simply be deleted, and each replacement pinned to the fenced call in the step that has to prescribe it. The audit gained the call it had been silently missing: it classifies master's CI three ways from a workflow run, and after the swap nothing prescribed a call that returns one — `list_workflow_jobs` needs a run id it had no way to obtain — so the night's own safety gate was left reading a value nothing fetched, and the field it compares is `head_sha`, not the removed CLI's `headSha`. The MCP-unavailable fallback also stops in the right place now: step 9 is commit, push and open-PR, and only the last of those needs MCP, so skipping the whole step would have left a night's work in a container that is gone by morning. Every one of those pins is the residue of a mutation that passed without it — a section-wide presence check survived deleting the fetch from the merge recipe, and a bare `create_pull_request` pin survived deleting the call from step 9 entirely, because in both cases explanatory prose still carried the name
- `docs/process.md` §5 now looks for Codex's approval where it actually arrives. When Codex has findings it creates a review object; when it has none it creates no review at all and posts a plain PR comment carrying `**Reviewed commit:** <sha>`. §5 knew only the first channel and, for the second, told the agent to wait for a 👍 reaction — which the cloud runner cannot read through any available tool. Approved PRs therefore sat in «На ревью» overnight. The reaction rule is gone rather than kept "for later", both observable channels are named in terms the reader can call, and the comment's sha is documented as a 10-character prefix so it is matched by prefix rather than by an equality that can never hold. `tests/test_process_review_signals.py` guards it. The same section gains a way out of the wait it used to have no exit from: 20 minutes of silence, then one `@codex review`, then 20 more. That call is bounded to one per HEAD commit rather than one per run — a card outlives the night, so a per-run bound would let each night spend another 40 minutes on the same silent PR — and it carries the sha (`@codex review (HEAD: <sha>)`), because a PR comment has no commit attached and a bare invocation cannot be told apart from last night's
- `docs/process.md` §5 again looks for Codex's approval where it actually arrives, because Codex changed its scheme and the previous fix aged out from the other side. There is no longer a fresh comment per iteration: Codex opens one `## Codex Review Summary` comment when the PR is opened and edits it in place — same `id`, same `created_at`, only `updated_at` and the body move — and when a review finds nothing it writes nothing else at all. The `**Reviewed commit:**` line §5 was told to match therefore stopped arriving in that channel: measured on PR #26, commit `09c1d01` was reviewed clean and `get_comments` carried no such line on any page, while the line survived only inside the review object of the *previous* commit, which is the findings channel. Read literally, §5 answered "not reviewed yet" for every clean HEAD — the failure PR #21 fixed, returning from the other side, and both #26 and #27 were merged by hand on a signal the document did not contain. The sign is now named as the summary's table row: `Code Review` with status `Completed` whose commit matches the start of the current HEAD. Two neighbouring things are written down as *not* the sign, because each is the obvious thing to reach for and each would restore the same overnight wait. The `Security Review` row is not compared with HEAD at all: it has its own trigger — PR opened, or an explicit call — and a push does not re-run it, so on PR #27 it sat on `9ee5569` through four subsequent commits while `Code Review` moved to `a3a193b`; a rule reading "every row on HEAD" would never converge. And the one machine-readable thing in the summary, the `codex-security-review:v1` HTML block, belongs to that same lagging review — its `headSha` held `9ee5569e1328…` while `Code Review` was four commits ahead — so leaning on it, the natural move in a document otherwise made of prose, would declare a stale commit reviewed. `Code Review` has no full sha anywhere in the summary, so the row has to be read as text. The prefix lengths differ between the two channels — 10 characters in the review body's `Reviewed commit`, 7 in the table cell — which is why the comparison is specified as "starts with" rather than as a slice of any fixed length. The merge gate names both halves of the sign rather than only the commit: a `Code Review` row on the current HEAD in any status but `Completed` means "still running", because the `Commit` cell moves to a new commit before the review of it finishes — a gate reading the cell without the status would merge an uncounted review, which is the failure step 10.2 already guards against with two halves of a condition instead of one, and it is the worse direction: the old bug left a PR asleep, this one puts it in master. The status literal is anchored to a captured row rather than to memory, since an unverified literal is the same never-converging trap one level down. `tests/test_process_review_signals.py` pins all of it to the paragraph that has to carry it rather than to §5 at large, on the same reasoning as the existing call-site pins: a fact stated somewhere in the section is not a fact available to the agent standing on the step. Each pin is a whole sentence rather than a fragment, because mutation testing cancelled every rule inside its own paragraph while the fragments survived word for word — «А вот строка `Code Review` … признаком как раз не является» contains the pin and means its opposite. A ban list was tried beside the pins and deliberately not kept: it killed nothing the whole-sentence pins did not, and seven rewordings walked around it in one sitting, two of them using no banned vocabulary at all. What would have to be forbidden is a second, contradicting prescription inside the region, and an enumeration is the wrong shape for that; keeping the list would have bought the look of a fence around a gap of the same size. The ban on reaching for a reaction is untouched and still whole-document — the boilerplate advertising one is printed inside the very summary comment this change teaches the agent to read
- Project repositioned as "TTRPG Session Transcriber" — open-source desktop tool for processing Discord game session recordings
- The `craig-start` marker now resolves to the nearest quarter hour instead of the nearest hour, so zones like UTC+5:30 and UTC+5:45 survive it
- Five settings that wrote to disk and were read by nobody are now visibly disabled and marked «СКОРО» rather than silently accepting input: the working folder (the session picker never asked for it), interface language (the project has no `QTranslator` at all), tooltips (no `ToolTip` exists in any screen), the completion sound (nothing in the project plays audio) and the Foundry OOC mode. OOC turned out not to be a wiring bug but an unbuilt feature — `ScriptMerger` takes no OOC parameter, no renderer looks at a message's channel, and the Foundry source stamps every message `"ic"` — so it joins the four rather than being fixed alongside the gap

### Fixed
- The timeline's right edge belonged to whatever was known when the folder opened — the chat's last message, a combat's end, or a four-hour floor — because track lengths are probed asynchronously and `build_window` runs before any of them exists. Players stop typing before they stop talking, so that edge routinely fell *inside* the recording, and the axis never grew to meet it. The reported symptom was lanes ending flush against the edge; measurement found worse. The tail of the audio is not compressed into the last pixel, it is cut off the axis entirely, and because a waveform is drawn across the `startPct..endPct` rectangle, five hours of sound stretched over a 255-minute window puts every peak at a wall-clock time it never happened at — 45 minutes adrift by the right-hand end. The window now grows when `PeaksWorker` reports a duration, through the `durationReady` signal it was already emitting. Where that signal goes is worth stating precisely, because two earlier attempts at this sentence got it wrong in both directions: it feeds `SessionMeta.totalSeconds`, and from there the ruler's fallback extent, the done-summary's session length, and `MergerWorker(total_duration=…)` — which uses it for nothing but the percentage on each `gapFilled` stitch marker. It never reaches `merged.txt`. So the signal was neither idle nor output-bearing: it drove several pieces of chrome, and not the axis. Growing the axis alone would have been a false fix: `SourceEntry` caches percentages computed against the window that existed at load time, so a wider axis with untouched rows leaves chat and combat still claiming 100% — the same flush edge, merely relocated — and the rows are now recomputed from retained timestamps rather than re-parsed. Only `t_end` moves: `ui/engines/asr_worker` measures every speech segment from `TimelineWindow.t0`, so shifting that would move transcribed speech in `merged.txt`, a change to merge output smuggled inside a drawing fix. The axis only ever grows, since durations arrive one track at a time in no order and a short track landing after a long one must not re-crop the lane that just fitted. It also settles a contradiction the report did not mention: once durations landed, the ruler said 255 minutes while the header caption said 300, so the screen disagreed with itself in two places visible at once
- `FEATURE_REQUESTS.md` stated four of its nine feature statuses wrongly, and `02_Статус_и_заметки.md` pointed at it as the product backlog with the words «статусы достоверны» — so the document was not merely stale, it was authoritative about being wrong. Feature #8 read «❌ не реализовано» while `renderers/combat_aware.py` shipped, was registered under `"combat-aware"`, was reachable from a «С разметкой боёв» dropdown and carried 28 tests; it also blamed a blocker («требует #3») that had been cleared, and cited the renderer registry at a line of `core/pipeline.py` holding an unrelated import. #3, #4 and #7 each carried two statuses that disagreed — `✅` in the heading, `❌`/`⚠️` below — and #3's lower block was false on three of its four claims, naming a hardcoded `startPct/endPct` that is computed, a combat dump that is parsed, and a ruler still in relative minutes that prints wall-clock hours. #3 carried one more contradiction in prose rather than in a marker: an owner's clarification from 21.04 still said, in the present tense, that the timeline offsets were «сейчас fake», directly under a `✅` status saying the axis is absolute — `SourceListModel.loadFromDir` has called `build_window` since iteration 3a. It is now quoted as the note it is, dated to when it was written, with the current behaviour stated beneath it. No guard catches this one: the checks read markers, not prose, and telling a stale sentence from a live one is a judgement rather than a comparison. The rot was structural rather than incidental: each section grew by appending a `> **Итерация N ✅**` blockquote at the top while the original request block below it stayed frozen at the day the feature was asked for, so the stale half was the half a reader met last. Statuses now match the code, the false line references are gone, and #8 has moved out of «🔮 Future» into the backlog it had in fact already shipped into
- `tests/test_feature_statuses.py` keeps that from happening again, and is deliberately narrow about how: it does not judge whether `✅` or `⚠️` is the better word for a half-finished feature — that is a product call — it checks only that the document does not declare a feature unbuilt while every named artefact of it sits in the tree. Three guards, because each is evadable without the others. A section's heading marker and its status marker must be the *same* marker: the weaker "no `✅` above a `❌`" would let a heading rename lift a section out of the check entirely, and for the five features with no evidence entry nothing else is watching them at all. A feature whose evidence is all present may not be declared unbuilt. And every section must carry a `**Статус:**` line with the verdict on that same line, since the other two read status lines and skip what they do not find — #1, #5 and #9 had no status line, and a verdict pushed onto the following line renders identically in Markdown while reading as an empty one, so either would have bought a silent exemption. Evidence is a path *and* a symbol inside it: the symbol names a call site rather than a bare name, because `from core.chunking import chunk_text_file` at the top of `core/pipeline.py` would otherwise vouch for a post-step deleted from `run()`, and it is matched with commented-out lines dropped, because a commented registry entry in `renderers/__init__.py` would keep vouching for a renderer nobody can select. A genuinely partial status stays sayable by marking it `(частично)`, documented in `FEATURE_REQUESTS.md` where the next writer meets it rather than only in the test — otherwise the one way to green the guard would be to overstate the feature, and it would push the document into a new lie to stop it telling the old one. The escape belongs to `⚠️` alone: on a `❌` it would let «не реализовано (частично)» wave a shipped feature through, which is the claim the guard exists to refuse. Four more ways out are closed with it — a heading stripped of its marker is a failure rather than "nothing to compare", a section duplicated instead of moved has both copies checked rather than only the last, `02_Статус_и_заметки.md` has to name *which* features are checked against code so the promise cannot outgrow the table, and feature #3 is evidenced through the GUI path it actually describes rather than only the CLI one. What the guard does not do is run the features: presence is not wiring, `SegmentJob` can exist while nothing constructs one, and closing that would mean booting Qt to read a Markdown file. The docstring says so plainly instead of leaving it to be discovered, and going further is filed as its own question. A status line inside a fenced or indented code block is not a verdict either — the legend now documents how to write one, so the first person to show an example would otherwise hand the parser a status and could then delete the section's real one unnoticed. Two further exemptions are closed, and they are worth telling apart from the parser's running battle with Markdown. A section ends at any *ATX heading of level 1 to 3*, not at `###` alone: while only `###` closed a block, a feature that had lost its status borrowed the verdict of the next `##` section and the heading comparison, seeing a marker on both sides, agreed. That exclusion had carried its own written justification — that closing on `##` would truncate the features under the `## 🔮 Future` divider — and the justification was false, since those features carry their own `###` headings and open sections regardless. Levels 1 and 2 are taken as a span so that a `#` added later needs no further patch, while `####` keeps belonging to the feature it sits in. The rule is stated in terms of ATX syntax rather than of heading level in general, because that is the part it can actually check: a setext heading (text underlined by `---`) and a heading inside a blockquote (`> ## …`) are headings too, are not matched, and can still hand a section the next one's verdict — left standing deliberately, as members of the unmodelled-construct family whose fate is an open question rather than one more patch. And a section may declare one *current* status and not two: nothing above could see a second `**Статус:**` line, because the heading comparison reads a marker from each and agrees when they match while the evidence guard is content as long as no line declares the feature unbuilt — so «✅ готово» followed by «✅ готово, но только на Linux» passed everything and left a reader no way to tell which verdict was today's. Every reader of `**Статус:**` lines asks the same question through one helper, and that uniformity is the point rather than tidiness: the rule arrived one reader at a time, and each partial state was its own defect — while one guard called a quoted line history and another called it today's verdict, a section could hold a verdict that one refused and another required, and a shipped feature recording its own past could be failed for the honesty. The same distinction decides what counts as *declaring* a status at all: a section left holding only a quoted `> **Статус:** ✅ было готово` renders with no current verdict, and a check that merely asked for a `**Статус:**` line somewhere would have passed it — the file answering one question two ways. Quoted lines are exempt, and that exemption is the rule rather than a softening of it: `**Статус:**` is read through a `> ` prefix on purpose, and this document's habit is to append a blockquote recording the status a feature *used to* hold — above the live one, so counting from the top would have called the historical line the verdict and reported the real one as the duplicate, failing the file for using the idiom the guard's own docstring describes
- Five defects the review surfaced in code rather than in the documents are recorded as known limitations next to the statuses they undercut, and filed as their own cards rather than fixed here. A session folder holding more than one chat log silently loses all but the first: the UI parses every log but builds the timeline window from `chat_paths[0]`, and the merge path takes `find_fvtt_chat_log`'s `matches[0]`, so the second file's messages reach neither the axis nor `merged.txt` and nothing counts or names them — the limitation is deliberate on the UI side, written into the code's own comment, but it was not written where a reader of the status would meet it. Speech drifts by the whole gap when chat or combat starts before the Craig recording: ASR offsets are measured from `TimelineWindow.t0` while `ScriptMerger` stamps the same events from `recording_start`, so a recording that began 107 minutes after `t0` puts speech from its first second 6420 seconds in, against chat at 180. A speaker-map edit reaches only the primary Craig segment — rows group by a normalised name while `speaker_map.json` is keyed by the full stem — so one player splits in two in `merged.txt`. The `_sources` cache outlives an edit, because the map and the ASR options are captured once at source creation and cleared only on cancel, which also makes feature #2's existing "restart the run" remedy wrong: `runAsr` does not clear the cache and only restarting the app does. And combat dumps go missing whenever `info.txt` lives inside `craig-1/` rather than at the session root, silently in the GUI and with a logged exception in the CLI. The claim that a full-width row makes a malformed dump visible was itself untrue and is corrected: there is no error role, badge, or log line, and the same full width is what a session with no `info.txt` legitimately produces
- The «Расширенные параметры распознавания» disclosure in the per-track model popover could not be clicked anywhere, so the block behind it never opened. What that block holds is a mock-up rather than working settings — the VAD tags carry no handler at all, the punctuation checkbox is bound to nothing, and language and beam size already work globally from the Settings screen — so the fix restores a control that was visibly broken rather than settings that were out of reach; the block's own state is filed separately. Its `MouseArea` sat directly inside a `ColumnLayout`, and a layout sizes its children itself: the requested `width: parent.width` was replaced by an `implicitWidth` of zero, and the `y: -20` meant to lift the zone onto the caption was replaced by the layout's flow position, putting it below the caption instead. Measured on the real popover, the zone was `w=0 h=20` against a 352px header. The header row is now wrapped in a plain `Item` the layout sizes, with the click target anchored to it — the same shape as the disclosure that works in `ui/qml/timeline/CastStrip.qml`. The popover is 13px shorter as a result, and that is deliberate rather than overlooked: sized to nothing but 20 tall, the broken zone sat in the layout as an empty 20px row under the caption, and the wrapper keeps 20 of it back as the height of the click target the broken zone had asked for — leaving a 13px difference where the accident used to pad
- «Открыть папку моделей» on the Models screen stayed grey after a model was installed, until the app was restarted. `enabled` was bound to `ModelRegistry.modelsRoot`, a plain `Slot` — and a QML binding over a plain method is evaluated once at component creation and never again, so the button latched the "no folder yet" state of a fresh install. `modelsRoot` is now a `Property` notified by `installedStateChanged`, the signal `_on_worker_done` already emits; it was the last member of that group still a bare slot. Nothing in the app recovered from this short of a restart — `refresh()` does not help either, because it re-emits a signal the binding was never listening to
- Three of the four session tabs — «Транскрипт», «Журнал», «Настройки сессии» — offered a pointing-hand cursor and did nothing when clicked: the screens behind them do not exist yet and their `tabActivated` signal had no listener anywhere. They are now visibly disabled, and the active tab is bound to screen state instead of a hardcoded literal
- «Макс. gap между репликами» in Settings never reached the merger. The GUI built its merge worker without a gap at all, so `ScriptMerger` glued replicas by the worker's own default whatever the field said — the value saved, redisplayed on restart, and changed nothing about merged.txt. It is now passed through, with the previous default kept for an unset or unparseable field so a fresh install merges byte-for-byte as before. One case does move: anyone who typed a number into the dead field back when it did nothing will see their merged.txt change on the next run — the setting they made is finally being honoured
- The UI, the timeline strip and the merger resolved the chat log's UTC offset three different ways and could disagree by whole hours on the same files. They now share one resolver
- The system-timezone step asked for today's offset instead of the session's, sliding sessions recorded across a DST boundary by an hour
- Chat messages and combat events recorded before the recording started were dropped silently; they are now reported
